## 一、问题从哪来

向量索引的构建期有三类事情会让人卡住，而且都发生在**构建开始之后**——也就是你已经等了很久之后：

| 现象 | 上游的表现 | 用户实际遇到的困难 |
|---|---|---|
| IVFFlat 构建内存不足 | `ERROR: memory required is N MB, maintenance_work_mem is M MB` | 报错发生在等了几分钟之后；而且报错里的 N **不是**你该设的内存值（见下） |
| HNSW 图放不下内存 | 只打一个 `NOTICE`，然后转磁盘继续 | 构建不失败，只是**慢几倍**，而且事后才知道 |
| 不知道还要等多久 | `pg_stat_progress_create_index` 只报"当前在哪个阶段" | 阶段之间没有可比口径，没有剩余时间 |

三类现象都已在本机复现并留档：`results/p0-20260826/`、`results/t35-20260827/`。

## 二、上游到底缺什么（这是立项依据，必须精确，不能夸大）

| 上游**已有**的能力 | 上游**缺**的能力 | 证据 |
|---|---|---|
| `IvfflatCheckMemoryUsage()` 在超限时报错 | 构建**开始前**判断会不会超限 | `ivfutils.c:121-129` |
| HNSW 有 `memoryTotal` 与 `FlushPages()` 落盘机制 | 事前预测**会不会降级、在第几行降级、内存下限该给多少** | `hnswbuild.c:507,530-549,724` |
| `pg_stat_progress_create_index` 报阶段名与阶段内计数 | 跨阶段可比的百分比、剩余时间预测 | PostgreSQL 自带视图；pgvector 自 0.2.3 起上报子阶段 |
| 7 个 GUC | 构建侧 GUC：**0 个**（7 个全在查询/扫描侧） | `results/t05-20260826/upstream_inventory.txt` |
| README 给参数方向（"调大 X 更好"） | 本机的**量**：调多少、代价多少 | `README.md:268,341,342,736` |

**表述边界**：不能说"上游没有内存管理"——它有。缺的是**事前预测**。
也不能把 `pg_stat_progress_create_index` 当成本项目的原创功能——它是 PostgreSQL 自带的。

## 三、需求 → 模块 → 验收证据

| 需求 | 模块 | 做成了什么 | 关键实测证据 |
|---|---|---|---|
| R1 构建前就知道 IVFFlat 会不会内存不足、报错会写多少 | M1 | 三检查点模型，复刻源码整数除法与 +1 取整 | 20 组矩阵逐字命中；SIFT1M 上 4/4 命中（含 208 MB、222 MB） |
| R2 知道**该给多少内存**（与"报错写多少"是两个数） | M1 补充 | `ivfflat_min_mwm_kb()` 取三检查点最大值 | 三配置边界**精确到 1 kB**（`need` 建成 / `need−1` 报错） |
| R3 构建前就知道 HNSW 会不会降级、在第几行、内存下限 | M2 | 从降级 NOTICE 反解 per_element，无需重编译 | 11/11 落在预测区间；外样本（60 MB）偏差 **0.12%** |
| R4 阶段耗时分解与跨阶段百分比 | M3 | 阶段权重按规模/数据集分档 + 顺序来自源码常量 | 3919 采样点单调；权重带样本数与极差 |
| R5 剩余时间预测，并说清有多准 | M3 T3.4 | ETA 偏差按 all/stable/unstable 三档量化 | L 档 MAD 42.33% → **29.08%**（修掉两个缺陷后） |
| R6 降级导致的耗时突变能否被 ETA 反映 | M3 T3.5 | 结论：朴素 ETA 反映不了；接入 M2 预测后可以 | 全程 MAD 59.10% → **9.02%** |
| R7 一条命令做完体检，输出能直接执行 | M4 | 零参数 `diagnose()`，每行四要素 | `pronargs=0`；TAP 断言四要素齐全 |
| R8 结论要分层：证据全留，默认只给可用的 | M4 | `stage_weight` / `_audit` / `_usable` 三层 | 不可用组保留并写明原因（极差 0.51 / 0.72） |
| R9 参数该怎么选，每个数字要有来源 | M5 (T2.7) | 三类溯源 + 帕累托前沿 | 6 个 HNSW 配置里 **2 个被支配** |
| R10 构建进行中就能看进度/剩余/风险 | M6 | 零参数 `build_monitor()` + 看板脚本 | 198 点单调，实时 ETA MAD **5.36%** |
| R11 异常场景下判定是否正确，尤其"说能建实际建不起来" | T4.3/T4.4 | 18 用例矩阵，四种判定口径 | `DANGEROUS` = **0** |
| R12 可复现、可回归 | 全局 | `reproduce.sh` 13 步 + 4 套 SQL 回归 + TAP | TAP 19/19；上游 `installcheck` 14/14、`prove` 1250 项全过 |

## 五、结论的适用范围（换机器/换数据必须重测的部分）

| 量 | 性质 | 换什么要重测 |
|---|---|---|
| `MAXALIGN(itemsize)`、`MaxHeapTuplesPerPage` | ABI 常数 | 换编译器或块大小 → `tools/abi_probe.sh` |
| `slot_coef`、`base_bytes` | 拟合 | 换 pgvector 版本 → `tools/hnsw_spill_probe.sh` |
| 降级减速倍数 4.031 | 拟合（磁盘快慢直接决定） | 换机器 → `tools/hnsw_eta_spill.sh` |
| 阶段权重 | 实测，按规模与数据集分档 | 换数据分布或规模 → `tools/measure_build_time.sh` |
| M5 的构建耗时与召回 | 实测 | 换行数/维度/数据集 → `tools/param_sweep.sh` |
| 三检查点公式本身 | 源码结构 | 换 pgvector 版本时复核 `ivfbuild.c` / `ivfkmeans.c` 行号 |

平台声明：只在 **CentOS 7 + devtoolset-11 + openssl11** 上实测过。
Rocky/RHEL 8+ 用 `gcc-toolset` 而非 `devtoolset`，`bootstrap_env.sh` 那条路**没测过**。

## 六、AI 使用说明

本项目的代码、SQL、脚本与文档在 AI 辅助下完成，人工负责选题、验收口径、
以及每个数字是否有证据的裁决。所有结论都必须能由 `reproduce.sh` 在干净机器上重跑得出；
凡是重跑不出来的，一律不写进结论层。今天这一轮里，
有三个缺陷是**被自己的量化步骤和边界测试抓出来的**（阶段顺序排错、无计数阶段进度冻结、
报错 MB 被误当成所需内存），过程与修法都留在 `docs/M1`、`docs/M3` 的补充章节里，没有隐去。
