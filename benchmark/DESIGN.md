# OpenTenBase 基准测试：第一性原理设计

## 1. 从问题本质出发

性能测试要回答的不是“某条 SQL 跑了多久”，而是下面三个可证伪的问题：

1. 在给定硬件、拓扑、数据量和并发下，系统能提供多少吞吐和多大延迟？
2. 并发增加后，吞吐为什么继续增长、趋于饱和或下降？
3. 观察到的限制来自 CN、DN、GTM、网络、磁盘、SQL 计划还是数据分布？

因此，一个结果只有同时带有运行条件、原始输出和跨层指标，才具有解释价值。单独的 TPS
数字不能在不同机器、不同节点数或不同数据规模之间直接比较。

## 2. 测量模型

本方案把一次测试拆成四层证据：

| 层 | 证据 | 回答的问题 |
| --- | --- | --- |
| 请求层 | TPS、平均延迟、失败事务、并发数 | 用户看到的性能是什么？ |
| SQL 层 | `EXPLAIN (ANALYZE, VERBOSE, BUFFERS, NODES)` | 时间花在哪个执行阶段？ |
| 数据库层 | 拓扑、连接、事务、每个 `xc_node_id` 的行数 | CN/DN/GTM 和数据倾斜是否相关？ |
| 主机层 | CPU、iowait、磁盘和网络吞吐 | 资源是否已经饱和？ |

四层证据使用同一个 run ID 保存。分析器只生成“瓶颈假设”，不把相关性写成已经证明的
因果关系。

## 3. 对照实验

分布式特征必须通过只改变一个关键变量的对照实验展现：

- 分布键点查与跨分片聚合：对比单 DN 路由和多 DN 扫描/CN 合并。
- 同分布 Join、复制表 Join、非同分布 Join：对比本地 Join、维表复制和数据重分布。
- 单语句写入与短事务：区分普通写路径和 GTM/事务协调开销。
- `1, 4, 16, 64` 并发矩阵：观察扩展效率、饱和点和延迟拐点。
- 每张分片表按 `xc_node_id` 统计行数：排除数据倾斜这一混杂变量。

每个正式样本都先预热，再按固定时长运行。测试顺序、数据规模、客户端数和工具版本写入
运行目录，避免“只保留最好一次”的选择偏差。

## 4. 最小实现边界

选择 PostgreSQL 兼容的 `psql` 和 `pgbench`，因为它们直接测量数据库协议路径，且不引入
应用框架开销。Python 仅负责编排、解析和报告，全部使用标准库。

没有引入 Prometheus、Grafana 或额外服务。它们适合长期监控，但会扩大部署变量，不是基础
基准的必要条件。主机采集器直接读取 Linux `/proc`，可在每台 CN、DN、GTM 物理机上独立
运行。

## 5. 失败语义

- 工具缺失、SQL 失败或 `pgbench` 非零退出时，默认立即停止。
- 原始日志始终保留；失败样本不会被静默丢弃。
- 密码只从 `PGPASSWORD` 或 `.pgpass` 读取，不写入配置或结果目录。
- 没有真实集群就不提交虚构数字；`results/` 中只提供明确标记的空模板。
