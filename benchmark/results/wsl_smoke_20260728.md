# Issue #202：OpenTenBase 基础性能测试与可复现基准工具

> 这是功能完整的单机 WSL2 烟测，不是生产容量报告。三次可比运行都从重建 schema 和相同
> 造数开始；结果可证明工具链与分布式执行路径有效，但不能外推到多物理机部署。

## 摘要

- 源码：`b612d77cbfd4d762f20c54c35f7caf09d57ef098`（OpenTenBase V5.21）
- 拓扑：1 GTM + 1 CN + 2 DN，全部位于同一 WSL2 虚拟机
- 数据：account 10,000；customer_order 100,000；order_audit 100,000；
  account_event 初始 100,000
- 矩阵：7 个 workload × 1/4/8 clients × 5 秒 × 3 次独立重置运行
- 延迟：pgbench 事务日志 100% 采样，报告 P50/P95/P99
- 完整性：63 个样本退出码均为 0，失败事务 0

## 分布式执行证据

- 分布键点查只命中 `dn0001`；计划为 `Remote Fast Query Execution`。
- 跨分片聚合命中 `dn0001,dn0002`，在 DN 上按 account 分组。
- 同分布 Join 在两个 DN 本地执行 account/order Join。
- 复制维表 Join 在两个 DN 各扫描完整的 64 行 region 表，再做本地 Hash Join。
- 重分布 Join 的计划明确显示 `Distribute results by S: order_id`；8 clients 时其中位 TPS
  513.92，比同分布 Join 的 862.44 低 40.4%，P95 从 11.390ms 增至 18.236ms。

数据倾斜不是这次 Join 差异的主要解释：四张分片表的 max/mean 行数比分别为 account
1.008、account_event 1.008、customer_order 1.008、order_audit 1.000。

## 主机证据与瓶颈边界

三轮综合采样的平均 CPU 分别为 1.9%、9.9%、10.4%；最高 iowait 为 5.4%、6.1%、5.3%；
峰值写吞吐为 99.4、126.1、142.8 MiB/s。第一轮采集窗包含较长空闲期，平均 CPU 不可与
后两轮直接比较。

由于 GTM/CN/DN/客户端全部同机，采样只能标记为 `combined`，不能归因到单独角色。所有
数据库流量走 loopback，而采集器默认排除 `lo`，所以网络列为 0 表示“未测到业务链路”，
不是“没有网络开销”。

当前最强证据支持的是 SQL 数据移动假设：重分布 Join 的计划和延迟/TPS 同时劣于同分布
Join。读与 Join workload 的 TPS CV 多数低于 10%；write/short_tx 的 CV 为 36%–73%，
说明 5 秒 WSL 烟测对写路径不稳定，不能据此定位 GTM、锁、磁盘或写容量瓶颈。

## 下一步正式实验

1. 在独立客户端、CN、DN、GTM 主机上运行默认 60 秒、1/4/16/64 clients、至少三次。
2. 每台机器显式选择业务网卡和数据盘，分别采集 CN/DN/GTM 指标。
3. 对重分布 Join 只改变分布键，复跑同等数据量以量化网络搬移成本。
4. 对 write/short_tx 延长到 60 秒并采集等待事件、锁和 GTM 指标，验证高 CV 来源。

## 可复现材料与 AI 使用

- 设计、runner、SQL、workload、主机采集器和聚合器均位于 `benchmark/`。
- `aggregate_results.py` 会校验三次环境签名与矩阵；不一致时拒绝聚合。
- AI 用于需求拆解、代码草拟和假设生成；版本、计划、TPS、延迟、分布与主机数据均来自
  真实命令输出。边界和人工复核记录见 [`AI_USAGE.md`](../AI_USAGE.md)。
