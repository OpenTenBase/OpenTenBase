# AI 使用策略自我报告

## 1. 使用的 AI 工具

本次文档工作使用 Codex 辅助完成资料定位、结构设计、初稿整理和语言检查。

## 2. AI 的使用范围

AI 主要用于以下工作：

- 将 Issue #200 的要求整理为可检查的交付清单。
- 从 README、部署工具文档和源码中定位术语候选及其证据。
- 设计“架构概览—SQL 流程—核心术语—易混边界”的文档结构。
- 生成 Mermaid 架构图初稿并检查术语表达是否适合新手。
- 检查 Markdown 链接、格式和前后表述是否一致。

AI 不作为架构事实的最终来源。所有技术描述都需要能回到仓库中的 README、部署文档或源码。

## 3. 核验方法

本次采用“先提出候选，再逐条找证据”的方式：

1. 从 Issue 和 `README_ZH.md` 提取 CN、DN、GTM 等核心概念。
2. 使用仓库搜索定位每个术语在部署文档和源码中的实现依据。
3. 对只能找到名称、无法确认职责的术语缩小解释范围或不采用。
4. 将最终事实依据集中列在新手导览的“事实依据与延伸阅读”一节。
5. 完成后检查链接、空白错误和完整 diff。

## 4. AI 输出的纠正与收窄

### 4.1 GTM 与查询执行

**候选表述：** 用 GTM 与所有 CN、DN 之间的实线箭头表达它对查询的控制关系。

**核验结果：** README 只明确说明 GTM 用于全局事务管理，没有支持“GTM 分解查询”或“GTM 执行分布式 Join”的说法。

**最终处理：** 架构图只用虚线表示 GTM 向 CN 提供全局事务管理能力，并明确说明该图不展开内部协议。查询分解职责归于 CN。

### 4.2 集中式模式

**候选表述：** 集中式模式只是组件更少、配置更简单。

**核验结果：** README 的集中式示例只配置 DN；`contrib/opentenbase_ctl/src/config/config.h` 进一步说明，该模式会忽略 GTM 和 CN 配置，只保留一组 DN。

**最终处理：** 使用源码可支持的具体描述，避免含糊地写成“配置结构更集中”。

### 4.3 Node Group

**候选表述：** 扩展解释 Node Group 如何决定数据路由和负载均衡。

**核验结果：** 当前核验材料可以确认部署工具根据 DN 创建默认 Node Group，但不足以在入门文档中概括所有路由语义。

**最终处理：** 只将其解释为 DN 的逻辑分组，并指出它不是物理服务器组或 Kubernetes Node Group。

### 4.4 一条 SQL 的执行范围

**候选表述：** 聚合查询一定会发送给所有 DN 并在 CN 完成最终聚合。

**核验结果：** README 支持“CN 将查询分解为 DN 执行的片段并收集结果”，但具体访问节点和算子位置取决于数据分布与执行计划。

**最终处理：** 改为“相关 DN 执行分配到本节点的工作”，并在图后明确实际涉及哪些 DN 取决于表、SQL 和执行计划。

## 5. AI 对效率的帮助

AI 帮助快速形成术语候选和统一的表达模板，也能在较短时间内交叉检查文档中的角色边界。最明显的帮助是把零散的 README 配置、安装日志和源码注释组织成一条适合新手阅读的主线。

与此同时，AI 容易把通用分布式数据库知识当成 OpenTenBase 的具体实现，或为了让图更完整而补充未被证据支持的关系。因此，本次没有采用“先生成全文再默认接受”的方式，而是以仓库内容逐项约束输出。

## 6. 总结

本次将 AI 定位为资料整理和表达辅助工具。AI 提高了检索、组织和检查效率，但最终技术内容以 OpenTenBase 仓库中的 README、部署文档和源码为准；无法核实的细节不写入交付文档。
