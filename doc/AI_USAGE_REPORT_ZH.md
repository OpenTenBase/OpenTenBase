# AI 使用策略自我报告

关联 Issue：#200（OpenTenBase 架构术语表与新手导览补充）

---

## 1. 使用的工具与定位

本次文档工作使用了大语言模型编程助手辅助完成资料检索、结构设计、初稿撰写和一致性检查。

**核心原则**：AI 只作为检索与表达的效率工具，不作为架构事实的来源。所有写入交付文档的技术结论，都必须能回溯到本仓库 `b612d77c` 基线上的 README、部署工具文档或源码。凡是只能依赖通用分布式数据库常识、无法在仓库中找到依据的说法，一律不写入。

---

## 2. AI 参与的具体环节

| 环节 | AI 的作用 | 人工负责的部分 |
| --- | --- | --- |
| 需求拆解 | 把 Issue 的 5 项要求整理成可逐条检查的交付清单 | 确认交付范围与优先级 |
| 资料定位 | 在仓库中定位术语对应的源码与文档位置 | 判断证据是否足够支撑该表述 |
| 结构设计 | 提出「概览 → SQL 流程 → 术语 → 分布策略 → 模式对比 → 易混边界 → FAQ」的骨架 | 决定章节取舍与顺序 |
| 初稿撰写 | 生成术语解释与表格初稿 | 逐条核对、改写、删除不可靠内容 |
| 双语一致性 | 检查中英文版本的术语数量与结论是否一致 | 最终定稿 |
| 格式检查 | 检查 Markdown 链接、表格、代码围栏 | 提交前复核 |

---

## 3. 核验方法

采用「先提候选，再逐条找证据」的流程，而不是「先生成全文再默认接受」：

1. 从 Issue 与 `README.md` / `README_ZH.md` 提取 CN、DN、GTM 等基础概念。
2. 对每一个术语，在仓库中定位其实现或配置依据，重点核对了：
   - `contrib/opentenbase_ctl/src/config/config.h`：配置字段语义与约束
   - `contrib/opentenbase_ctl/src/cluster/cluster.cpp`：节点组创建逻辑
   - `src/backend/parser/gram.y`：分布类型语法定义
   - `contrib/opentenbase_ctl/README.md`：工具子命令
   - `src/gtm/README`：GTM 源码结构
3. 对只能找到名称、无法确认具体职责的术语，缩小解释范围或不予采用。
4. 把最终依据集中列在文末的「事实依据索引」，便于评审者逐条复核。
5. 完成后检查链接有效性、表格闭合与完整 diff。

## 4. 被纠正或收窄的 AI 输出

以下是本次实际发生的纠正记录，均为 AI 初稿中存在、经源码核对后修改的内容。

### 4.1 集中式模式的含义

- **AI 初稿表述**：集中式模式是把 GTM、CN、DN 三个角色合并部署在同一台机器或同一实例中。
- **核验结果**：`config.h` 中 `ConfigFileInstance::type` 的原始注释明确写着「centralized代表集中式，此时会忽略gtm和协调节点的配置，只有1组数据节点」。`README_ZH.md` 的集中式示例也只配置了 `[datanodes]`。
- **最终处理**：改为「忽略 GTM 和协调节点配置，只构建一组 DataNode」，并在易混边界表中专门列出这条，提醒读者不要把分布式查询路径套用过来。这是一处会直接误导新手的错误，必须纠正。

### 4.2 分布策略的枚举范围

- **AI 初稿表述**：OpenTenBase 支持 Hash 分布与复制表两种方式。
- **核验结果**：`gram.y` 的 `OptDistributeByInternal` 规则显示语法层面实际支持 `SHARD`、`HASH`、`MODULO`、`REPLICATION`、`ROUNDROBIN` 五种类型，并且额外兼容 `DISTRIBUTED BY`、`DISTRIBUTED RANDOMLY`、`DISTSTYLE` 等 Greenplum 风格写法。
- **最终处理**：补全为五种类型并列出兼容语法表。同时补充一句风险提示：语法支持不等于所有版本执行路径完全等价，遇到 `Cannot support distribute type` 类报错应以实际构建行为为准，避免把语法定义误当作能力承诺。

### 4.3 Node Group 的成员范围

- **AI 初稿表述**：Node Group 是节点的逻辑分组，可包含 CN 与 DN，用于资源隔离与负载均衡。
- **核验结果**：`cluster.cpp` 的 `build_create_node_group_cmd()` 在遍历节点时明确跳过所有非 `NODE_TYPE_DN_MASTER` 的节点，生成的语句形如 `CREATE DEFAULT node group default_group with (dn0001,dn0002);`，随后执行 `CREATE sharding group to group default_group;`。
- **最终处理**：改为「DN 的逻辑分组」，补充默认组名 `default_group` 与实际 SQL，并删除当前证据不足以支撑的「负载均衡」表述。

### 4.4 GTM 在查询链路中的位置

- **AI 初稿表述**：用实线箭头把 GTM 画进查询主链路，暗示它参与查询调度。
- **核验结果**：README 只说明 GTM 用于全局事务管理；`README_ZH.md` 补充其管理集群事务信息与全局对象（如序列）。没有任何依据支持「GTM 拆分查询」或「GTM 执行分布式 JOIN」。
- **最终处理**：架构图中 GTM 改用虚线，并在图下方明确说明它不承担查询拆分与数据存储，内部协议不在本文展开。

### 4.5 一条 SQL 的执行范围

- **AI 初稿表述**：聚合查询一定会下发到所有 DN，并在 CN 完成最终聚合。
- **核验结果**：README 支持「CN 将查询拆分为在 DN 执行的片段并收集结果」，但具体访问哪些节点、算子落在何处，取决于数据分布与执行计划。
- **最终处理**：改为「相关 DN 执行分配到本节点的工作」，并补充一条性能直觉说明：命中分布键时可路由到单个 DN，未命中则需访问多个 DN。既保持准确，又给新手可操作的认知。

### 4.6 未采用的内容

以下 AI 建议因证据不足或超出新手导览范围，未写入文档：

- 具体的哈希算法实现细节与分片映射公式。
- 「在线重分布可在不中断业务的前提下平滑扩容」这类能力承诺——当前核对材料不足以支撑该结论。
- 具体的性能数字与 TPS 对比——本次未进行基准测试，不应写入。
- GTM 内部协议与 GTS 时间戳机制的细节描述。

## 5. AI 的实际帮助与局限

**帮助**：最明显的价值是把分散在 README 配置表、安装日志、C++ 头文件注释和语法文件中的信息，快速组织成一条适合新手阅读的主线，并在双语版本之间保持结论一致。检索与交叉核对的效率提升显著。

**局限**：AI 有两个稳定的失误倾向。一是把通用分布式数据库知识当成 OpenTenBase 的具体实现，第 4.1 和 4.3 节就是典型例子。二是为了让图表和列表「看起来更完整」，主动补充未被证据支持的关系。因此本次没有采用一次性生成全文的方式，而是以仓库内容逐项约束输出，并保留了纠正记录。

---

## 6. 结论

本次交付物中，文档结构、术语取舍、证据核对与最终定稿由人工负责；AI 承担资料检索、初稿生成与格式检查。所有技术结论以 OpenTenBase 仓库 `b612d77c` 基线的 README、部署工具文档和源码为准，无法核实的细节不写入交付文档。
