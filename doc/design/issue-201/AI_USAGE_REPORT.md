# AI 使用策略自我报告

关联 Issue：#201
仓库基线：`b612d77c`

本报告按 issue 评价标准要求的「调研、比较、验证、修正」四个阶段组织，记录 AI 在本次方案设计中的实际参与方式，以及被源码推翻的具体判断。

---

## 0. 核心原则

**AI 不作为 OpenTenBase 行为的判断依据。**

Kubernetes Operator 是一个通用知识密集的领域，AI 在这方面的输出流畅且看似合理。这恰恰是最大的风险：它容易把「其他分布式数据库通常怎么做」当成「OpenTenBase 就是这么做的」。

因此本次采用一条硬规则：**任何关于 OpenTenBase 的技术断言，必须能定位到仓库中的具体文件与行号；否则要么标记为待验证假设，要么删除。**

这条规则在第 4 节产生了 4 处实质性纠正，其中 2 处如果不纠正会导致方案根本性错误。

## 2. 比较阶段

AI 完成了 CNPG 与 OpenTenBase 的逐维度对比，人工重点复核了其中「差异是否被夸大或缩小」。

对比过程中确立了一个判断标准：**差异是「量的差异」还是「质的差异」**。

- 量的差异（可复用）：存储管理、单节点流复制、监控采集、声明式模型。这些只是对象更多，机制相同。
- 质的差异（必须新建）：拓扑目录持久化、GTM 独立角色、分片元数据、多角色引导顺序。这些在现有 Operator 中没有对应概念。

这个区分让「可复用约 50%」这个结论有了依据，而不是凭感觉给的比例。

### 3.2 编写可执行校验

为了让「验证」不停留在口头，编写了 `poc/validate.py`，把上述约束编码为断言。它只用标准库，评审者零环境成本即可复现。

其中最有意义的两条断言：

- **集中式示例不得出现 `gtm:` 与 `coordinators:` 段** —— 直接防止把分布式模型误套到集中式。
- **`BootstrappingGTM` 在 `BootstrappingDN` 之前** —— 把引导顺序约束固化为结构检查，而非只写在文档里。

### 3.3 明确未能验证的部分

没有可用的 Kubernetes 集群，也没有搭建 OpenTenBase 集群做故障注入。因此以下内容**全部标记为未验证**，写进设计文档第 9 节的风险表（R1 至 R7）：

- Headless Service FQDN 是否超出 host 字段长度限制
- `ALTER CLUSTER GTM NODE` 在 GTM 已宕机时的行为
- 在线分片重分布的阻塞程度与恢复语义
- StatefulSet 顺序约束对 failover 的实际影响
- GTM 可导出的指标清单
- 目录注册中断的恢复效果
- 分布式一致性备份的可行路径

这些同时被写成讨论帖的 Q1 至 Q5，用于向社区求证，而不是自行给出看似确定的答案。

## 4. 修正阶段

以下是 AI 初稿中的判断被源码推翻或收窄的完整记录。

### 4.1 GTM 故障切换的处理方式（根本性错误）

**AI 初稿**：GTM 主节点故障后，Operator 需要进入所有 CN 和 DN 容器，修改 `postgresql.conf` 中的 `gtm_host` 参数，执行 `pg_ctl reload`，再调用 `pgxc_pool_reload()`。

**核验过程**：先在 `contrib/opentenbase_ctl/src` 中搜索 `gtm_host`，只命中 `--master_gtm_ip` 这类命令行参数，没有配置文件写入。顺着 `master_gtm_ip` 追到 `src/bin/initdb/initdb.c`，发现 `load_gtm_info()` 执行的是 `create gtm node ... host='...'` —— 这是一条写系统表的 SQL。

**结论**：初稿方案**完全无效**。GTM 地址不在配置文件里，改 conf 加 reload 不会产生任何效果。

**进一步查找正确路径**：在 `gram.y` 中搜索 GTM 相关语法，找到 `ALTER GTM NODE` 与 `ALTER CLUSTER GTM NODE`。再确认 `cluster` 标志的语义，在 `utility.c:973` 发现它会设置 `exec_type = EXEC_ON_ALL_NODES`。

**最终方案**：GTM failover 通过 `ALTER CLUSTER GTM NODE` 完成，并在 CRD 中设为默认策略 `gtmFailoverStrategy: alterClusterGtmNode`。同时诚实标注该路径在故障场景下未验证（R2），并列为讨论帖 Q2。

这是本次最有价值的一次纠正。如果沿用初稿，整个 failover 设计会建立在错误前提上。

### 4.2 数据分布与端口模型过度简化

**AI 初稿**：每个节点监听一个端口（类比 PostgreSQL 的 5432），Kubernetes 中直接暴露即可。

**核验过程**：在 `utils.cpp` 中读 `get_available_port_pair()`，发现一次分配 3 个连续端口，且 `types.h:72` 明确注释 forward_port「与 node port 相邻」。同时注意到探测函数带 SSH 凭据参数。

**最终方案**：CRD 中显式定义 `ports.node` / `ports.pooler` / `ports.forward` 三个字段，默认 11000 / 11001 / 11002，并说明 Kubernetes 中因 Pod 网络隔离可改为静态约定、无需 SSH 探测。

### 4.3 Node Group 的成员范围

**AI 初稿**：Node Group 是节点的逻辑分组，可用于 CN 与 DN 的资源隔离与负载均衡。

**核验过程**：读 `build_create_node_group_cmd()`，其遍历中显式 `continue` 掉所有非 `NODE_TYPE_DN_MASTER` 的节点。

**最终方案**：明确 Node Group 仅由 DN 主节点构成，并在 CRD 注释中标注依据。删除「负载均衡」这一无证据支撑的表述。

### 4.4 分片扩容的自动化程度

**AI 初稿**：Operator 检测到 `shards` 增加后，自动完成节点注册与数据重分布，实现「一键扩容」。

**核验过程**：仓库中未找到能支撑「在线重分布安全可控」的实现证据。无法确认阻塞粒度、耗时特征与中断恢复语义。

**最终方案**：明确划定边界 —— Operator 负责 Pod 拉起与目录注册，**不在 reconcile 循环中执行数据重分布**，由独立 Kubernetes Job 承载。同时在设计文档 7.2 节明确声明「本方案不声称能自动安全完成这一步」，列为 R3 与讨论帖 Q3。缩容则建议第一版直接拒绝而非尝试执行。

宁可缩小承诺范围，也不写出无法验证的能力声明。

### 4.5 StatefulSet 的选择理由（收窄而非推翻）

**AI 初稿**：使用 StatefulSet 是显然正确的选择。

**核验过程**：CNPG 的公开设计明确**不使用** StatefulSet，理由是顺序约束会阻碍故障转移控制。这说明该选择存在真实的技术争议。

**最终方案**：保留 StatefulSet 作为初步选择，但补充了完整的权衡说明（设计文档 6.2 节），并明确标注「这是待验证的初步选择，不是最终结论」，列为 R4 与讨论帖 Q4。

### 4.6 未采用的 AI 建议

| 建议 | 不采用原因 |
| --- | --- |
| 补充完整的 Operator Go 代码骨架 | 超出 issue 要求的设计范围，且无法验证正确性 |
| 给出具体的性能数字与扩容耗时预估 | 无测试数据，属于编造 |
| 声称方案「已通过验证，可直接落地」 | 没有 K8s 集群，连 CRD admission 都未验证 |

## 5. 效率评价与局限

**帮助**：AI 在源码检索与结构组织上效率明显。特别是从 `--master_gtm_ip` 这个命令行参数一路追到 `initdb.c` 的 SQL 生成函数，这种跨文件的调用链追踪如果手工进行会慢很多。文档骨架与双向对比表格的初稿质量也可用。

**局限**：AI 在本任务中的失误集中在一个模式 —— **用通用分布式系统经验填补 OpenTenBase 的具体实现细节**。第 4.1 节的 GTM 配置误判是最典型的例子：把「大多数数据库的地址配置在配置文件里」直接迁移到了 OpenTenBase，而实际上它写在系统表。第 4.2 与 4.3 节同源。

这类错误的共同特征是**表述自信、逻辑自洽、但事实错误**，仅凭阅读无法发现，必须回到源码。

**据此形成的工作方式**：不接受任何未定位到源码的 OpenTenBase 断言；对每个关键设计决策先问「支撑它的事实在哪个文件的哪一行」；把验证结果写成可执行脚本而非文字承诺。
